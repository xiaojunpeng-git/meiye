# R64: platform group stock-policy regression

Read-only 008 diagnosis identified activity 1 / root 7351 / branch 7365: product_type=5, is_inventory=0, both root/branch stock=0 and retail is_show=0, while the active group has 100 places at 1 yuan. Earlier fixtures were store-owned and stocked, hiding this platform-only failure. No credentials, member data or order data are included in the catalog evidence.

The confirmation validator now uses the existing authoritative catalog stock policy already used by group add-to-cart. Only physical products with inventory enabled AND negative stock disabled require store stock. Rights and inventory-disabled/negative-allowed products retain their independent activity capacity. Catalog existence/deletion and independent store ownership are checked explicitly; activity applicability remains enforced. Ownership may not depend on an accidental out-of-stock rejection.

The fix is one backend service. Two existing tests were extended; no frontend business code, schema, config or history changes. Comments document authority, scope, ownership and deferred group quota. The source authority remains the original cart/catalog/activity and order transaction; no duplicate fact/event source is created. Group quota is still locked/consumed during creation; receipts remain pending until group completion. Payment stock validation remains the existing inventory service.

Rollback-only local MySQL tests use platform/off-retail/zero-catalog-stock fixtures at 1 yuan. Products, cards and projects confirm, retain item/price/store, create one unpaid order, pass the REAL pre-payment stock guard, consume one place, leave catalog stock at zero, and replay idempotently. Also cover explicit applicability rejection, independent-store ownership, quota exhaustion, inventory disabled with negative disabled, managed negative allowed, managed shortage blocked by BOTH confirmation/payment, and managed sufficient branch stock. Rights stay nonphysical even if an inventory flag is enabled. The actual frontend hydration and submit validator consume these controller responses. Original owned-store modes and payment/consumption-visibility contracts pass. SQL rolls back; fixture Redis/config caches are cleaned. No real payment or production order is executed.

Seven inventory/catalog/create/quote dependencies in the working source match the accepted release baseline exactly. Candidate identity is in fixed-version.json. This new candidate is not committed or deployed; PM acceptance and publication gates still apply. No mini rebuild is needed for this backend correction. Existing pending upload tasks are separate and have not been resent.
