# C17：完整答案模型链路提速 — 自测记录

日期：2026-09-15（本机开发实例）

## 目标与边界

优化目标是缩短用户从提交问题到看到**完整、经过语义复核的答案**的时间；“任务已接收”不计为答案提速。

常规请求原本串行经历三次模型调用：

1. 自然语言理解；
2. 能力边界内的候选绑定；
3. 候选绑定的独立语义复核。

本轮将前两项合为一次模型调用：一次响应中包含独立的 `understanding` 与 `intent` 两个载体。服务端仍分别按原契约校验，且在 Reader 前保留独立复核。因此没有以关键词、固定指标、固定日期或绕过复核来换取速度。格式异常或排名候选不唯一时仍允许受限的额外模型步骤，不能把异常路径伪装为正常路径提速。

## 真实模型测量

同一台本机应用容器、同一已启用模型配置、同一脱敏问题“今天现金业绩多少？”、同一最小注册候选、无 Reader 查询。只输出阶段耗时、结构状态和模型用量；未记录 API Key、客户数据、答案或模型原文。

| 路径 | 理解/合并 | 绑定 | 独立复核 | 模型总耗时 | 结果 |
| --- | ---: | ---: | ---: | ---: | --- |
| 旧三步路径 | 12,909ms | 7,780ms | 1,406ms | 22,096ms | 通过，复核接受 |
| 新两步路径（样本 A） | 10,116ms | — | 892ms | 11,009ms | 通过，复核接受 |
| 新两步路径（样本 B） | 11,522ms | — | 798ms | 12,321ms | 通过，复核接受 |

该受控样本中，模型段由 22.1 秒降至 11.0–12.3 秒；它证明合并协议能够真实运行并减少一次串行模型往返。样本数量不足以宣称生产 P50/P95 或完整页面端到端提升。发布前或发布后仍须以同账号、同问题的浏览器完整答案耗时补充正式基线。

## 本机完整链路实测

随后用已有的本地授权夹具执行了一次完整链路：当前 `admin` 可信身份、当前数据权限、真实模型、真实 Reader、异步接纳和本机常驻执行 Worker。问题为“今天现金业绩多少”；夹具不打印问题答案、对象或凭据，只留下真实 Run 记录供页面或数据库的既有留存机制查看。

| 阶段 | 实测 |
| --- | --- |
| bootstrap | 27ms |
| create（已可靠接纳） | 43ms |
| create 至 Worker 产出 `COMPLETED` | 15,206ms |
| 最终状态 | `COMPLETED`，无失败原因 |

这说明本机完整执行已经由已接纳任务走到真实答案完成，而不是只测模型客户端。它仍不是浏览器绘制完成时间，也不能替代线上 P50/P95；此前线上约 38–39 秒的观察样本与本次账号、数据、队列负载并不相同，不能直接把两者相减后宣称固定提速比例。

## 尚未宣称完成的事项

- 本记录不是线上性能基线，也不代表完整浏览器答案已完成 P50/P95 对比。
- 本轮没有部署、没有重启线上消费者、没有改变模型配置或人员权限。
- 上线时，新的 Worker 代码必须与应用代码一起滚动重启；否则常驻 Worker 仍可能运行旧的三步路径。
