# OPT1｜按需引导与上下文衔接：会员补充超时修复（R3）

状态：**开发与自测完成，待产品经理对本报告固定版本明确确认验收**。未提交、未部署、未 push。历史失败保留，本报告不将此前失败或未验路径改写为通过。

## 已查明的问题

用户原问题“会员王丽在上个月消费多少”先确认统计指标，再等待完整手机号。原 Run `eec61d33aa4f7e9c87ee86acf89eedaa84d970a9553bb61a` 在本地记录中于 21:29:48 发出手机号补充步骤，21:39:41 达到累计十分钟等待边界。仅指标选择被接受，手机号未被接受，也未执行事实查询。因此原页面提示不能解释成“会员没有消费”或“手机号码错误”。

原实现等待补充时停止轮询，页面没有按服务端截止时间刷新，过期卡片仍能填写。迟到提交收到终态后又落入通用失败提示；原条件和用户刚填的草稿没有可继续的交互。

本轮真实复测还发现：在已确认姓名、指标、日期后，仅补充完整手机号仍再次调用外部模型。一次旧卡片恢复实际发生连续两次约 30 秒传输超时，尚未执行查询。这不证明上游超时的具体原因，但证明身份补充不应依赖重新解释已确认的业务问题。

## 修复内容

1. **准确显示等待截止边界。** 后端投影既有累计十分钟截止时间与服务端时间；平台工作台在截止时安排一次状态读取，由后端判定过期。刷新页面也重新按当前服务端时间安排，不新增输入期间的持续轮询。
2. **过期原因与可执行恢复。** 迟到提交或状态读取确认过期后，显示“补充等待已超时，尚未执行查询。已确认条件已保留，可继续原查询。”保留当前补充草稿和原步骤；刷新后可从该对话历史恢复。只提供完成该缺项所需的表单和“继续原查询”，不回退到无关的重试/改题/新对话答题卡。
3. **原上下文由服务端恢复。** “继续原查询”通过现有 create 接口提交受限来源凭证和本次选择；服务端核验账户、终端、会话、设备、原 Run、步骤及当前权限、能力、模型配置，恢复加密保存的原条件。浏览器不拼接问题、不提交查询计划。新 Run 正常执行准入、幂等、并发和预算；旧 Run 保持失败，不延长原等待时限。异步工作输入只在加密载体中保留受限来源凭证，队列仍仅传 Run ID。
4. **明确的身份缺项本地完成。** 仅当服务端已经形成完整的会员单项汇总请求、且只等待身份确认时，私有引导记录保存已确定的指标、绝对日期、门店约束与待确认姓名。回复只含一个合法完整手机号时，按当前授权会员关系精确匹配，唯一匹配后进入原编译器和统一 Reader，不再发送模型请求。未匹配继续核对手机号；仍多重匹配作为数据绑定冲突结束，均不冒充零消费。其他自然语言补充继续语义理解，未写死姓名、号码、日期或某个问句。
5. **共用原执行逻辑。** 正常澄清与过期恢复共用一个选择编译方法；保留当前事实、冲销、权限、单位和金额口径。无新 Skill、接口、配置、数据库迁移或另一套任务状态机。

## 设计与数据边界复核

- 业务权威源、事实粒度、冲销、金额“分”精度与“元”整数展示、后端数据权限沿用注册指标 Reader；无客户端金额计算、数据库结构变更或业务事实写入。
- 新 Run 重验当前能力与授权；最终会员选择仍由本地关系服务和 Reader 复验。恢复不接受浏览器提交的会员 ID、指标代码或扩大后的门店范围。

- 本次编译方法提取替代了 clarify 分支内重复实现；引用扫描确认正常补充与过期恢复均调用同一方法。原完整句携带手机号、非纯号码补充及旧卡片兼容路径仍有调用，保留。无废弃的空选择恢复分支或平行身份查询实现。
