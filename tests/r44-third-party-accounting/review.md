## 实现边界

| 场景 | 取值与约束 |
| --- | --- |
| 新会员普通购买、充值 | 创建时冻结 `member_commerce_order.accounting_method`；真实渠道、商户及交易号保留在支付凭据，回调仍校验金额、渠道与交易号。 |
| 新拼团及其他原单活动购买 | 控制器会员来源经 `StoreOrderCreateServices` 冻结 `store_order.accounting_method`；原单组织权限、成团履约及状态可见性保持不变。 |
| 历史订单、升级前已创建待付单 | 默认空标记，无迁移回填；之后付款仍按原渠道记账。重试返回原订单，不生成新标记替代。 |
| 余额及混合支付 | 对用户的记账名称统一，内部仍区分 `member_balance`；外部收款及现金业绩只取真正外部到账部分。 |
| 零元单 | 冻结记账分类但不制造收款行；“记账收款”无金额行时继续显示空占位，不伪造“第三方支付 ¥0”。 |
| 列表、筛选、详情、导出 | 普通订单及原单先使用各自统一 Reader 投影，再进入共享订单中心筛选；详情和导出使用同一名称与收款明细。平台/门店没有新增分支。 |
| 原单财务报表 | 在统一收款 Reader 中按冻结标记归入第三方支付；原实收资格、金额、业务日和权限不变，余额不纳入外部收款。 |

## 人工入口保护

- 手动收银目录 `checkoutCatalog()` 排除 `third_party`；前端收款方式配置代码不新增此选项。平台配置管理可以看到固定名称的记账字典，该行不等于人工收款入口。
- 收银快照准备和最终锁定的销售提交分别校验可信服务端 `actor_type=member`；人工充值同样校验。
- 记账方式更正的入口、候选目录及提交均使用原 `ACTUAL_METHODS` 白名单，第三方支付不在其中，不能由人工更正伪造。
- 代码核对涉及 `MemberOrderAccounting`、两类会员结算服务、`StoreOrderCreateServices`、共享订单查询及投影、`CashierV3BusinessConfigServices`、`CashierV3CheckoutPreparationServices`、`CashierV3SaleOnlyCheckoutSubmissionServices`、`CashierV3RechargeModule` 和 `CashierV3PaymentMethodCorrectionServices`。
