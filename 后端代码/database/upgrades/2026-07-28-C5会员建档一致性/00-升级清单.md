## 权威数据与一致性边界

- `eb_user` 仍是会员档案权威源，会员编号继续写入既有 `bar_code`，不建立第二套会员编号。
- 新会员编号由单行序列串行分配，生成后还必须查询 `eb_user.bar_code` 做全系统冲突检查；历史空值和重复值不在本包静默修复。
- `eb_member_exclusive_service` 是会员当前专属服务人的权威关系；`eb_member_exclusive_service_change` 是不可覆盖的变更历史。
- `member.created` 由统一业务事件表记录，并与会员主表、门店关系、编号和专属服务人处于同一 Gateway 事务。本包不再建立会员专用 Outbox。
- 本包不建立会员事实大表，不以 Outbox JSON 替代会员主表或可查询关系表。
- 旧 `eb_cashier_v3_member_event_outbox` 只允许不存在或为空；01 和 03 都会检查，预检后的新增行同样阻断。

## 变更范围

1. 新建 `eb_cashier_v3_member_phone_lock`：规范化手机号行锁资源，关闭“手机号不存在时无法锁行”的并发窗口。
2. 新建 `eb_cashier_v3_member_number_sequence`：保存 9 位会员编号序列游标；初始化 `member_bar_code=99999999`，首个候选号为 `100000000`。
3. 新建 `eb_member_exclusive_service`：每名会员最多一条当前专属服务人关系。
4. 新建 `eb_member_exclusive_service_change`：保存原人员、新人员、来源、原因和操作人历史快照。
5. 为既有 `eb_user.bar_code` 增加普通索引 `idx_bar_code(bar_code)`，加速会员编号冲突检查和查询。

`idx_bar_code` 不能直接设为唯一索引：历史库存在大量空字符串，且上线前尚未完成全量历史编号清洗。新编号唯一性由“序列行锁 + 事务内冲突检查 + 失败重试”保证；历史清洗完成后再单独评估唯一约束升级。

## 明确不包含

- 不回填历史空会员编号，不改写已有会员编号。
- 不删除或合并历史重复手机号、重复条码。
- 不迁移旧 `salesman_id` 为专属服务人，不猜测旧字段语义。
- 不连接远程数据库，不自动执行四库 SQL，不部署代码。

## 执行顺序

1. 备份目标数据库并核对真实站点、库名、表前缀和最低 MySQL 版本。
2. 核对 `SHA256SUMS.txt`。
3. 确认 `20260727-001` 与 `20260728-003` 均已登记，并分别通过三表、四表精确结构合同。
4. 执行 `01-升级前检查.sql`。允许四张会员目标表全部不存在，或四张均已是完全兼容结构；缺依赖、旧专用 Outbox 非空、部分建表、同名异构、升级键已使用均会主动失败。
5. 执行 `02-正式升级.sql`。
6. 再执行一次 `02-正式升级.sql`，确认可安全重复，且不得新建旧会员专用 Outbox。
7. 执行 `03-升级后验证.sql`，必须输出 `VERIFY_OK`；该步骤再次复核依赖结构和旧专用 Outbox 窗口。
8. 完成新增会员、重复手机号并发、会员编号冲突重试、专属服务人写入和统一事件同事务业务验证；`member.created` 应为一行事件、零 Outbox。
9. 业务验证通过后，才写入目标库 `eb_database_upgrade_log` 并更新数据库升级总表。

## 性能与锁表风险

- 四张新表创建不扫描旧业务数据。
- `ALTER TABLE eb_user ADD INDEX idx_bar_code(bar_code)` 会扫描并锁定 `eb_user`；本地约一万行不代表生产规模，必须在目标库低峰执行并提前评估耗时。
- 升级期间不得并发发布依赖该索引和新表的会员建档代码。
