# 回滚或应急说明｜20260728-002-cashier-v3-member-consistency

## 首选应急方式

先关闭 V3 `create-member`、专属服务人设置及自动绑定写入口，保留所有新表和统一事件数据。不得通过删除会员、改汇总数字或覆盖变更历史来“回滚”。

MySQL DDL 会自动提交，本包不能宣称事务回滚。执行前必须备份目标库。

## 按执行阶段处理

### 尚未启用业务写入

只有同时取得查询证据并满足以下全部条件，才属于“可回滚空态”；任一条件不满足都按“已产生数据”处理：

- `eb_member_exclusive_service` 为 0 行；
- `eb_member_exclusive_service_change` 为 0 行；
- `eb_cashier_v3_member_phone_lock` 为 0 行；
- `eb_cashier_v3_member_number_sequence` 恰好只有 1 行；
- 该唯一行必须是 `sequence_key='member_bar_code'` 且 `current_value=99999999`，表示编号序列从未推进；
- 已关闭所有依赖这四张表的代码入口，目标库备份已验证可恢复。

满足上述条件后，仍须由 Codex 针对已核对的目标库另行生成一次性回滚 SQL，按依赖逆序处理；本说明不提供可直接复制执行的 `DROP`，避免误删已进入使用状态的数据。

`idx_bar_code` 默认保留。只有升级前留存的结构快照明确证明该索引原本不存在，且本次执行记录明确证明它由本包创建，才允许在独立变更窗口评估删除。缺少任一份证据时不得删除；删除普通索引同样可能锁定 `eb_user`。

### 已产生会员或关系数据

禁止直接 DROP、TRUNCATE 或重置序列。应：

1. 停用写入口。
2. 保留 `eb_user.bar_code` 和已分配编号，编号永久不得重用。
3. 保留当前专属服务人及变更历史。
4. 统一业务事件与 Outbox 由 `20260728-003` 的应急方案管理，本包不得删除或改写。
5. 修复代码或另建新升级键，不原地修改已在任一目标库成功执行的升级包。

## 一致性故障

- `eb_user` 已有会员但缺 `member.created` 事件：按命令回执、会员 ID 和创建时间生成可审计修复任务，不重复新增会员。
- 事件已有而会员不存在：视为事务边界破坏，立即停止相关消费者并调查；不得把事件当成会员权威源。
- 专属服务人当前关系与历史不一致：以业务命令、当前关系版本和变更记录共同对账，使用新的变更记录修正，不覆盖旧历史。
- 序列游标异常：停止新增会员；核对所有 9 位 `bar_code` 后再通过独立修复升级推进游标，禁止回退游标。

## 不可执行操作

- 不删除已分配会员编号。
- 不把序列值改小。
- 不用事件或 Outbox payload 覆盖会员主表。
- 不在未备份、未核对目标站点时执行任何 DROP 或 ALTER。
