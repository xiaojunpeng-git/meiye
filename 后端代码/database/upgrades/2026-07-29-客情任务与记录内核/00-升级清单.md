## 权威边界

- `eb_customer_care_task` 是客情任务当前状态的权威源，用户状态只允许 `UNSTARTED`、`IN_PROGRESS`、`COMPLETED`、`VOIDED`。
- “删除”只把未开始任务的 `is_visible` 改为 `0` 并写 `deleted_at`，不新增 `DELETED` 状态、不物理删除。
- “转派”只更新当前负责人和任务版本，并追加操作记录，不新增 `REASSIGNED` 状态；首期目标负责人必须在任务业务门店有效任职，禁止跨店转派。
- `eb_customer_care_record` 同时承载任务完成记录与日常独立客情记录。`task_id` 可空；同租户多个 `NULL` 可保存多条独立记录，非空任务仍由唯一键限制为至多一条正式记录。正式内容不提供覆盖更新；仅允许 `NORMAL -> VOIDED`，原内容和原时间永久保留。完成时如选择下一次跟进，记录显式保存下一任务、计划时间和负责人快照；下一任务来源固定为 `PREVIOUS_FOLLOWUP`。
- 每条正式记录显式保存记录类型、实际跟进时点、实际跟进人、可选关联业务及其名称快照。`business_date` 按 `followed_at + 业务门店时区快照` 计算；`occurred_at`、`settled_at`、`recorded_at` 只使用命令真实成功时间，不能被历史跟进时间倒填。
- 日常手工录入的 `followed_at` 不得晚于服务端当前时间，也不得早于当前时间约五年（`158112000` 秒）；更早历史只能通过单独的受控迁移与对账导入。
- `eb_customer_care_operation` 是领域操作审计，只追加，不是统一业务事件、Outbox 或经营事实。命令抢占和重放复用 C1 的 `eb_cashier_v3_command_receipt`，占位、领域写入、operation 和回执完成处于同一事务；共享 Gateway、统一事实层和报表接入另立闭环。
- 共享回执的客情私有映射固定为：物理幂等键 `CARE_RECEIPT-<由 tenantId + 原命令键稳定派生的标准 UUID>`，action `CARE_<operationType>`，state context `CARE_CONTEXT-<租户稳定 UUID>`；原客情幂等键、资源 ID、正版本、业务/操作门店和操作人保存在规范化请求指纹及 `contexts_json/hash`。该映射不冒充浏览器工作台上下文，也不得被 C1 归档工具按异常前缀删除。
- 计划逾期按 `planned_at < 服务端当前时点` 且任务仍为未开始/进行中判断，不按自然日文字或前端本地时间重算。

## 数据架构自检

- 权威业务源：任务、正式记录和操作审计分别落三张明确粒度的表；不复用事件 JSON 作为任务主表。
- 最小粒度：一行任务、一项任务的一条正式跟进记录或一条独立日常客情记录、一条成功领域命令的一项操作审计。
- 时间：任务保存计划/开始/完成/作废/删除时间；正式记录保存 `business_date`、`occurred_at`、`settled_at`、`recorded_at`；操作保存真实发生与系统记录时间。
- 事务/并发/幂等：命令先在 C1 共享回执表原子占位，再按 task→record 的固定顺序加锁；现有资源命令要求正 `expectedVersion` 并使用 CAS。完成任务、正式记录和可选下一任务在同一事务全成或全回滚，operation/回执冻结下一任务标识和版本。相同幂等键并发只能有一个执行者，其他连接等待首事务后读取不可变成功回执；失败事务连同占位一起回滚，可用同一键安全重试。
- 作废/历史：任务进入 `VOIDED` 或记录进入 `VOIDED`，不覆盖原记录内容；删除只隐藏；全部变化追加 operation。
- 维度/权限：业务组织、组织路径、业务门店、操作组织、操作门店、会员、负责人和操作人均有明确列及名称快照；负责人有效性读取统一 `employee` 主档及 `system_store_staff.employee_id` 任职关系。共享层后续从登录态和组织主数据强制注入权限范围。
- 事实/报表：本包不写经营事实、不提供统计；后续统一事件/事实接入必须与成功业务事务同边界完成。
- 性能：任务按门店/负责人/会员/组织路径+计划时点索引；记录和操作按业务日期/发生时点索引。所有 ASCII 组合键远低于 767 字节。
- 历史兼容：不修改、不回填旧客情或旧回访表；旧模块保持兼容冻结，后续切换需单独对账。

1. 备份并核对目标数据库、真实 `eb_` 前缀和最低数据库版本。
2. 核对 `SHA256SUMS.txt`，确认目标库已登记 `20260719-009-employee-org-leader` 与 `20260727-001-cashier-v3-command-idem`，统一员工/任职结构及共享命令回执表通过结构校验，并且没有登记 `20260729-001-customer-care-core`。
3. 执行 `01-升级前检查.sql`，必须输出 `PRECHECK_OK`；任一目标表已存在都停止，不猜测或自动修复部分结构。
4. 执行 `02-正式升级.sql`；该文件的 `CREATE IF NOT EXISTS` 只支持同一固定文件安全重放，不代表接受结构漂移。
5. 执行 `03-升级后验证.sql`，必须输出 `POSTCHECK_OK` 并保留 EXPLAIN 结果。
6. 若 DDL 中断后只留下 1 至 2 张目标表，停止正常升级，执行 `05-部分创表恢复.sql`。它只做无损校验：已存在表必须零行且列/索引/引擎/排序规则与 `02` 精确一致；0 张表、完整 3 张表、登记表缺失、任何异构、非空或已登记状态都会拒绝。输出 `PARTIAL_DDL_RECOVERY_READY` 后直接执行同一固定版本的 `02 → 03` 补齐缺表，禁止重跑要求零目标表的 `01`。`05` 不包含任何目标表 `DROP`，并发变化最多令 `03` 失败，不会删除数据。
7. 完成代码合同、迁移静态门禁和真实 MySQL 5.6 独立验收后，才允许按发布流程登记升级键。
