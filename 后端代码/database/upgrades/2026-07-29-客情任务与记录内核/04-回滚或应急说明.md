# 回滚或应急说明｜20260729-001-customer-care-core

## 首选应急方式

先关闭后续共享层注册的客情查询和写命令入口，保留三张表与操作审计。MySQL DDL 会自动提交，本包不能宣称事务回滚；执行前必须完成目标库备份。

当前内核没有注册路由、Gateway、事件消费者、统计或手机端接口。若后续接入失败，应先停用接入层，不得删除、覆盖或从操作日志反写任务/正式记录。

## DDL 中断后的部分创表恢复

若 `02-正式升级.sql` 因连接中断只创建了 1 至 2 张目标表，不得继续执行要求零目标表的 `01`、不得手工 `DROP`，也不得把现存同名表当作本升级表。应在已核对的目标库执行 `05-部分创表恢复.sql`：

- 升级登记表必须存在且结构可查询，升级键必须尚未登记；
- 所有已存在目标表都必须为 0 行；
- 每张已存在表的列顺序、类型、可空、默认值、字符集、排序规则、索引、引擎和表排序规则必须与 `02` 精确一致；
- 恰好只能存在 1 至 2 张目标表；0 张表应走正常 `01 → 02 → 03`，完整 3 张表应直接执行 `03` 核验，二者都拒绝进入部分恢复；
- 升级登记表缺失、任一目标表异构、非空或升级键已登记时，整批停止；
- `05` 永远不删除、不改写目标表。只有输出 `PARTIAL_DDL_RECOVERY_READY` 后，才可直接执行同一固定版本的 `02 → 03`，由 `CREATE TABLE IF NOT EXISTS` 只补缺表并由 `03` 做完整精确核验。

该脚本只识别尚未产生业务数据的失败 DDL，不是业务回滚工具，也不能用于已登记升级。恢复期间必须保持客情入口关闭；即使校验后发生并发写入，后续流程也没有目标表删除动作，`03` 只会安全失败并要求人工核对。

## 尚未产生业务数据

完整升级已经成功但尚未产生数据时，只有同时满足以下条件，才可由 Codex 针对已核对的具体目标库另行生成一次性回滚 SQL；不得用 `05` 代替完整回滚：

- 已关闭全部客情读写入口和后台任务；
- `eb_customer_care_task`、`eb_customer_care_record`、`eb_customer_care_operation` 均为 0 行；
- 目标库备份已经验证可恢复；
- 没有任何已部署代码、报表、手机端或事件消费者依赖这三张表；
- 已核对升级登记状态并取得具体环境的发布授权。

本说明不提供可直接复制执行的 `DROP` 或 `TRUNCATE`，避免误删错误站点或已产生的历史。

## 已产生任务、记录或操作

禁止 DROP、TRUNCATE、物理删除任务、覆盖正式记录内容、把版本改小或复用旧幂等键。应：

1. 停止新命令入口，保留操作审计与请求指纹。
2. 任务状态异常时按自然键、命令幂等键、版本和 operation 顺序核对，不直接改统计结果。
3. 正式记录错误时只允许走 `NORMAL -> VOIDED` 的受控命令，保存原因和操作人；不得覆盖原跟进内容、实际跟进人、关联业务或四类时间。
4. 发现漏写 operation、事件或事实时，先确认事务边界和来源命令，再通过新的可审计恢复任务处理。
5. 如需结构变更，创建新的 `upgrade_key`，不得改写已在任一数据库执行的本升级 SQL。

## 明确禁止

- 不把删除实现为 `DELETED` 状态或物理删除。
- 不把转派实现为 `REASSIGNED` 状态，也不改变任务当前业务状态。
- 不跨店转派，不把页面提交的门店/组织范围当作后端权限。
- 不使用创建时间、自然日标签或前端时间代替 `planned_at` 判断逾期。
- 不用 `followed_at` 倒填 `occurred_at`、`settled_at` 或 `recorded_at`；历史跟进时间只决定记录的业务归属日。
- 不把 operation 当作统一业务事件、Outbox、正式记录或报表事实。
- 不在未通过双重验收与发布门禁前执行四库 SQL、部署、commit 或 push。
