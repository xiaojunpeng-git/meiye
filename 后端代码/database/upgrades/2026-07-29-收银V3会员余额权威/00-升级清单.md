# 收银 V3 会员余额权威升级清单

- 升级键：`20260729-009-cashier-v3-member-balance-authority`
- provider 合同：`cashier-v3-member-balance-authority-v1`
- writer 合同：`cashier-v3-member-balance-writer-v1`
- 权威源：`eb_user` 的 `now_money`、`ben_money`、`give_money` 与同一行 `balance_version`。
- 版本推进：MySQL 5.6 `BEFORE UPDATE` 触发器观察三项余额真实变化并将 `balance_version` 严格加一；禁止金额哈希、时间戳或影子版本。
- 流水：继续复用 `UserBalanceAtomicServices` 与 `eb_user_money`；本升级只补齐其本赠金变化、稳定幂等键和指纹列及唯一索引。
- 金额：接口与结账事实使用整数分；旧余额主表和旧流水保持定点两位小数。适配器在边界做无浮点转换。
- 扣减顺序：先扣本金，不足部分再扣赠金；保存本金、赠金和总额的 before/change/after。
- 事务：最终结账调用方持有唯一外层事务；会员主行、流水、销售/收款/事实/Outbox 任一步失败全部回滚。
- 数据权限：服务端强制 tenant、member、store、operator；`none` 和 `self_participant` 不允许执行余额扣款。
- 激活：本包不修改 Bootstrap、Gateway、manifest、路由或前端，不激活 action。

## 旧写路径审计

旧系统存在多条直接更新 `now_money` 或本赠金分量的路径，例如旧余额支付、充值、抽奖、新人赠送、会员卡激活、人工调账、导入及销户。逐文件补版本容易漏写，也不能阻止未来旧代码新增旁路，因此版本必须由数据库在真实主行统一推进。

触发器只负责观察版本，不静默纠正旧数据。若某会员不满足：

```text
now_money = ben_money + give_money
```

迁移仍可安装版本观察能力，但该会员的 V3 余额查询和扣款必须 fail-closed。`03-升级后验证.sql` 会输出待对账数量和明细；必须完成有来源、有审批的余额对账后，才能让对应会员使用 V3 余额扣款。

## 执行顺序

1. 备份目标库，进入维护窗口并暂停所有旧端和新端余额写入。
2. 执行 `01-升级前检查.sql`；仅在输出 `PRECHECK_OK` 后执行 `02-正式升级.sql`。
3. 执行 `03-升级后验证.sql`，保存余额不一致清单；验证结束前不得恢复余额写入。
4. 若中途失败，执行 `05-部分升级恢复审计.sql`；只有输出 `PARTIAL_UPGRADE_RECOVERY_READY` 才能重跑正式升级。
5. 代码与数据对账均通过后，按真实 SHA、固定代码版本和执行人登记升级日志，再按发布门禁恢复写入。

本升级当前仅在唯一源码正本内创建；未授权远程执行、部署、历史余额修复、commit 或 push。
