# 收银 V3 正式销售订单权威升级清单

- 升级键：`20260729-011-cashier-v3-sales-order-authority-v1`
- 合同：`cashier-v3-sales-order-authority-v1`
- 权威来源：最终结账事务内已加锁的 `cashier_v3_checkout_request` 聚合。
- 粒度：每个含正式成交商品/卡项/项目的结账请求固定一张正式销售订单；每个 `sale` checkout line 固定一条订单明细。
- 纯权益边界：`entitlement_only` 只形成核销/服务结果，不形成销售额或销售订单，本 writer 必须拒绝。
- 游客：`member_id=0` 合法，不能因未选会员阻断正式订单。
- 明细类型：仅 `product`、`card`、`project`；混合结账中的卡内权益服务行只作结账追踪，不冒充销售行。
- 金额：整数分，逐行满足 `原价 - 优惠 = 销售额`，主单合计必须与锁定结账请求一致。
- 幂等：同租户结账请求、自然键、订单号和服务端 ID 均有唯一约束；相同命令及不可变载荷只读重放，漂移必须拒绝。
- 历史：保存商品/卡项/项目的名称、编码、分类和组织门店快照；后续改名不反改历史订单。
- 时间：`business_date` 沿用最终锁定结账口径；`occurred_at` 使用最终结账命令真实发生时间，不冒充较早的准备时间；`settled_at`、`recorded_at` 由服务端最终事务提供。
- 状态预留：V1 只写 `settled/forward/version=1`；未来退款、作废和冲销必须另立合同，禁止覆盖原始金额与快照。
- 激活边界：本包不修改 Gateway、manifest、CashierModule、前端或 C5 旧销售订单查询，不激活 `submit-checkout`。
- 旧表边界：不读取、不写入、不迁移 legacy `store_order`；历史兼容和新旧读模型合并另立任务。

执行顺序：

1. 针对产品经理明确点名的单一客户实例，独立核对当前 commit、迁移版本、数据库、Redis/进程共享依赖、备份和回滚点。
2. 执行 `01-升级前检查.sql`；仅在输出 `PRECHECK_OK` 后继续。
3. 执行 `02-正式升级.sql`。
4. 执行 `03-升级后验证.sql`；仅 `POSTCHECK_OK` 可登记成功。
5. 若多表 DDL 中断，先运行 `05-部分创表恢复.sql`；仅 `PARTIAL_CREATE_RECOVERY_READY` 可重跑正式升级。
6. 按 `SHA256SUMS.txt` 校验固定文件，并逐实例登记结果；一个实例成功不代表其他实例完成。

本升级当前仅作为本地源码正本，不授权远程执行、部署、历史回填、commit 或 push。未被点名的实例保持原状。
