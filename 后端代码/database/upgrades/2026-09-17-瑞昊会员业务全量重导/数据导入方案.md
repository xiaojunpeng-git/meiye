# JSJ → ruihao 数据导入方案

本方案记录本次已验收的业务口径，并作为以后 **JSJ → ruihao** 导入的执行基准。每一轮仍由产品经理下达导入指令、指定来源数据截止时间和范围；不得把本次验收当作未来自动清库授权。同目录 PHP 是本次批次的实现记录，含写死的 `2026-09-17` 筛选日期和 `JSJ-20260917-R1` 批次标识；**以后不得原样重跑**，必须先按本方案改成新批次参数、完成预检和自测。

## 1. 适用范围与执行方式

- 来源库固定为 jsj，目标库固定为 ruihao。`jsj` 是产品经理维护的唯一导入来源；后续不得创建、读取或依赖任何 JSJ 数据副本／冻结表。目标守卫不通过时立即退出，禁止写入其他库。
- 覆盖会员主档、余额、普通项目权益、项目赠送、产品赠送、寄存、预售、长期卡、卡欠款及充值欠款。
- 当前采用直接来源重导：以执行时的 `jsj` 为唯一权威来源，清除本轮约定范围内的旧业务事实和旧会员资产，再从 JSJ 重建。不能因旧订单、服务、核销或预约已经发生就自行保留；下一轮清理前仍须重新核对目标实例、清理清单和当时的经营影响。
- 清理后保留会员、商品、项目、卡项、SKU、门店、组织、权限、配置等必要主数据及稳定来源 ID 映射；随后从当次 JSJ 重建会员余额、普通权益、项目赠送、产品赠送、产品寄存、产品预售、长期卡及欠款。重建生成的卡订单、持卡记录、项目明细、充值投影及欠款 authority 是**本次导入载体**，不是保留下来的旧销售事实。
- 不创建或读取 JSJ 业务事实的持久副本。执行 SQL 的临时表只在连接内用于关联与分片；来源 ID → 目标 ID 映射及清理审计可持久保留以保证追溯、唯一性和重跑幂等，但不能充当余额、余次或欠款的第二权威源。

## 2. 导入前门禁

1. 明确本轮 JSJ 数据截止时间、目标实例 `rh` 的 `ruihao`、批次 ID、业务范围及清理范围。只读核实数据库主机、库名、站点对应关系、当前代码/迁移版本和共享依赖；不能仅凭数据库名称判断实例。
2. 目标库备份由产品经理自行负责；Codex 不创建或保管 `ruihao` 备份。清理前核对产品经理已完成可恢复备份、回滚点和业务停写/维护窗口，并记录各清理表的行数。未具备这些条件不得开始删除。
3. 直接读取 jsj。导入前记录来源连接标识、各类权益数量、最大业务时间和最大主键，作为本轮对账依据；不在 ruihao 或其他库创建 JSJ 数据副本。
4. 映射会员、平台商品、门店子商品和 SKU。商品赠送、寄存、预售等会员资产以目标会员为唯一导入匹配键；门店字段只作为现有表结构的记录信息，不得因门店不存在、门店归属不同或来源门店无法确认而过滤会员资产。会员存在跨店业务时，所有导入业务记录统一使用该会员的 `belong_store_id`，来源门店只保留追溯用途。
5. 会员资料同步覆盖 `jsj.bd_Customers` 全量资料；即使新会员没有当前资产，也要增量创建或更新到 `ruihao`。同手机号来源合并为一个目标 uid，历史来源键均映射到该 uid；空手机号使用稳定内部键，不伪造真实手机号。
7. 清理采用 `05-清理业务数据.php` 的**显式表白名单**，先 dry-run 记录表级数量，再以 `--execute --allow-ruihao --clear-business-facts` 执行并保存清理审计。不得改成全库 `DROP`、通配表名或按模糊订单号删除。

### 清除与保留边界

| 处理 | 范围 | 关键判定 |
|---|---|---|
| 清除旧业务事实 | 旧销售订单与明细、收款/充值/消费流水、服务记录、核销、预约占用、退款/作废、欠款与还款、赠送事实、业绩、经营聚合、命令回执/Outbox、库存批次/台账/出入库/预警 | 只清本方案确认的白名单；关联的旧卡订单、持卡记录、旧权益项目明细及商品领用投影也清除。旧事实为零与本次重建载体有数据可以同时成立。 |
| 重置旧资产数值与投影 | `eb_user` 的余额三字段、商品及 SKU 的销量/库存计数、指向已删除订单或充值的来源映射 | 余额重置后才从当次 JSJ 计算；销售/库存计数不能继续引用被清除的事实。 |
| 保留并更新主数据 | 会员主档与唯一手机号、会员所属门店、门店/组织、商品/项目/卡项、SKU、必要关联、权限与配置 | JSJ 新会员增量建档；已有会员按来源键和手机号合并，不以跨店业务门店筛掉资产。必要缺项先补承载及映射。 |
| 保留追溯键 | 来源会员/商品/卡号映射、门店别名规则、清理审计 | 只作关联与审计，不作为旧 JSJ 余额、余次或欠款副本；下次重用前校验映射指向有效目标。 |
| 从 JSJ 重建 | 会员余额、普通项目权益、长期卡、项目赠送、产品赠送/寄存/预售、卡欠款/充值欠款，以及运行这些资产所需的卡订单、持卡、项目明细、领用与还款 authority | 使用本轮来源统计和来源键逐项对账；不能把本次重建记录误算成应清零的旧事实。 |

`05` 白名单是本次实际清理边界。以后如果系统增加业务事实表，必须先完成依赖盘点、加入白名单并扩展清理后零值验收，不能假定旧脚本自动覆盖新表。清理审计记录每表删除行数；用户备份是回滚来源，清理审计和来源映射都不能代替备份。

## 3. 导入口径

### 会员与余额

- 会员资产匹配唯一依据是目标会员 ID；门店不参与是否导入的判断。目标表需要门店字段时统一填充目标会员的 `belong_store_id`，不能用来源门店或门店内连接把会员资产过滤掉。
- JSJ 余额没有本金和赠金拆分时，全部按本金导入。
- 金额在来源聚合后按标准四舍五入到整数；次数和数量按目标字段精度保存，并保留来源值用于对账。
- 每位导入会员必须满足：总余额 = 本金 + 赠金。
- 商品赠送、寄存、预售明细必须按会员逐条对账；会员映射成功即允许写入，禁止使用 `eb_system_store` 内连接或来源／目标门店一致性条件作为导入门槛。

### 普通卡与项目权益

- 每一条来源权益必须映射到正确的卡项目、门店项目和项目 SKU，且项目归属门店必须等于订单门店。
- 普通卡订单、卡主明细、会员卡持有记录和项目权益明细必须同批建立。
- 项目权益金额同时写入 total_price 和 pay_price。正价权益不得出现总价大于 0、实付金额为 0。
- 每条权益必须保存项目展示快照 cart_info.productInfo.store_name，且名称必须等于其关联的门店项目名称；禁止页面回退显示“项目”。

### 长期卡

- JSJ 长期卡按 V3 time 规则承载。
- 每张长期卡必须同时存在：卡订单、持卡记录、专用“长期项目”明细、规则状态和规则组件。
- 规则状态、组件、持卡人、订单、项目和不可变快照必须彼此一致。长期卡不得以普通项目次数或普通金额替代其时间卡语义。

### 赠送、寄存与预售

- 项目赠送作为项目权益导入，并保存来源 ID、项目关联和项目名称快照。
- 产品赠送、寄存和预售按各自来源表和来源 ID 分别导入，不按名称合并。
- 预售／寄存写入可领用投影；没有来源领用流水时不得伪造历史领用记录。

### 欠款

- 卡欠款和充值欠款都必须导入欠款主记录、欠款明细和对应 V3 authority。
- 充值欠款必须同时创建充值投影；只写欠款主记录会造成后续补交失败。
- 欠款金额保留正负业务含义，冲销或抵扣不得转写为正债权。

## 4. 固定执行顺序

1. 由产品经理完成目标库备份；Codex 仅确认目标守卫为 ruihao。
2. 直接读取 jsj 执行来源一致性检查，记录各类动态来源统计、最大业务时间和最大主键；截止时间、权益有效期筛选日及批次 ID 必须同属本轮，不能沿用脚本内的 `2026-09-17` 常量。来源未达到声明截止时间、映射阻断或来源在导入期间变化时停止清理/续导，重新对账。
3. 运行会员、门店、商品和 SKU 映射及阻断检查。
4. 在产品经理确认备份完成后，按清理白名单清空旧业务事实和旧导入载体，并重置余额、库存和销量投影；清理后先核对旧服务、核销、预约、还款、业绩、库存等旧事实为零。
5. 先完成全量会员资料合并与来源 ID 映射，再补商品/项目/卡项、门店子商品和 SKU 承载。随后按依赖顺序重建：余额及普通卡项目权益 → 项目赠送与项目快照/金额校正 → 商品赠送/寄存/预售 → 长期卡及规则快照 → 卡欠款与充值欠款及 authority。每类先核来源键和映射，再写目标；失败只重试幂等分片，不重复整库清理。
5a. 所有资产均随**会员所属门店**落库；跨店来源记录不能决定归属或成为过滤条件。本次脚本按会员属店落库，但没有可指定门店的独立执行参数；不能把整表脚本同时启动多份冒充逐店并行。后续若要逐店并行，先补门店参数、幂等/锁和门店级对账。
6. 对同手机号来源强制写入同一目标 uid，并核验清理范围内的旧业务事实已清空。
7. 运行直接读取 JSJ 的导入后验收，对余额、权益、赠送、商品、长期卡和欠款做来源/目标数量、金额/次数、来源键双向差集及门店归属对账；同时确认旧销售、服务、核销、预约、业绩、看板和库存业务事实已清零。当前 `11-导入后验收.php` 覆盖其中一部分数量和结构检查；下轮执行前须补齐会员资料、商品三类、余额总额、来源键双向差集和清理白名单的全表零值检查，不得将 `passed=true` 单独解释为所有业务口径均已验证。
8. 运行会员权益跨门店可见性专项检查：必须验证“有权益的会员”在当前操作门店打开详情时，卡项权益仍按会员返回；不得因为会员归属门店、卡项记录门店或当前操作门店不同而把会员详情判定为不存在。
9. 只有验收脚本全部通过后，才在收银端进行人工业务验证。

## 5. 必过验收项

导入后验收以本轮直接读取 jsj 的动态统计为准，必须全部通过：

- 普通项目权益、项目赠送、长期卡、卡欠款、充值欠款及两类欠款 authority 的来源／目标数量一致。
- 非空手机号重复分组为 0。
- 导入会员余额结构错误数为 0。
- 正价普通权益实付金额为 0 的数量为 0，普通权益总价与实付金额不一致数为 0。
- 长期卡规则状态与规则组件数量都等于来源长期卡数。
- 项目关联失效、项目跨门店、项目名称快照缺失、项目名称快照不一致均为 0。
- 会员权益可见性专项检查必须通过：至少抽查一个会员归属门店与当前操作门店不同的样本，在收银端“权益明细”中能看到卡项和项目明细；接口 `open-member-detail` 与 `load-member-detail-tab(tab=assets)` 均须返回成功且卡项数量大于 0。
- 摘要有权益金额或次数时，“权益明细”不得为空；跨店会员仍能看到普通项目的真实名称和长期卡的“长期项目”。

人工验证至少覆盖：余额、普通项目权益次数和金额、长期卡“长期项目”、项目赠送、产品赠送／寄存／预售、卡欠款补交、充值欠款补交、同手机号会员。

重导清理后必须核验：旧销售订单、服务记录、核销事实、预约占用、退款/作废、业绩、看板聚合和库存业务流水均为 0；本次 JSJ 导入载体不能计入“旧销售订单”。本轮会员资产和必要主数据数量与本轮来源一致。

以后每轮沿用本方案的**清除/保留边界、直接 JSJ、会员属店、手机号唯一、映射补齐、资产重建、对账和收银端抽查**；清库前核对当时新产生的业务事实及备份，重新记录截止时间、批次和验收结果。
