# 瑞昊历史消费欠款商品关联修复

## 范围与口径

- 目标实例仅为瑞昊 `rh.cc3798.com` 的独立 `ruihao` 库。本闭环只处理补交单 `BJ26100800005`，不批量改动同批 894 条历史欠款。
- 权威来源为原始 `jsj` 消费明细的商品 ID、原消费欠款补导的 `source_key`、既有旧商品到平台商品映射及门店子商品映射。名称只能用于缩小来源查询，不能用名称决定商品 ID。
- 本单来源商品 `bd_goods:0091001456`，目标门店商品 `462363`；其当前分类为“花园 / 花园产品”。
- 仅为 `eb_store_debt_item.id=325335` 补充缺失的商品关联。欠款额、补交收款、销售业绩、事实和原商品名称均不改动。薪资明细和汇总复用既有报表读取器，随商品当前分类显示。
- `01-修复.php` 默认只读。写入必须同时指定 `--execute --allow-ruihao` 与当次预检返回的 `--expect` 指纹，且只接受一个明确补交单号。执行会在同一事务中更新一条欠款明细并写入独立审计行。

## 发布门禁

1. 对当前源码固定版本完成语法、执行保护、瑞昊只读预检及金额/来源/分类对账，交产品经理明确确认验收。
2. 验收通过后仅暂存本闭环文件并本地提交；提交前核对暂存 diff，不夹带其他任务脏改动。
3. 产品经理已授权本闭环瑞昊线上修复，但执行前仍须核对线上实例、当前代码/迁移版本、备份、回滚点和当次预检指纹。线上只运行已提交的本地正本脚本，不在服务器手改业务源码。
4. 独立备份瑞昊 `eb_store_debt_item` 表及本单修复前行，记录路径与校验值。此前“不备份本地库”不取消生产实例备份。
5. 执行后核对：欠款明细仅一行 `product_id=462363`；审计表仅一行生效记录；补交金额 ¥1,010、对应业绩事实数额及行数不变；员工薪资明细分类变为“花园 / 花园产品”，汇总分类金额归属同步更新，总金额仍不变。
6. 若核对失败，用 `02-回滚.php` 的精确审计指纹回滚商品关联，并复核报表、金额和审计状态。回滚脚本默认也只读；生产回滚须在异常处置时明确执行。

## 数据架构自检

- 本任务不产生新经营事实、不改变结账或补交成功时点，业务主表及历史事实金额保持原状。
- 唯一修复粒度是一条已导入欠款的商品身份；以旧系统消费分组哈希和旧商品 ID 双重定位，防止同名、跨店或多商品合并误关联。
- 现行商品分类属于报表读取维度，历史名称快照不回写。原始补交状态、日期、幂等键、冲销链路及数据权限不变。
- 单行写入通过事务、行锁、旧值条件、唯一审计键和预检指纹保护；失败回滚，重复执行不能新增事实或重复记账。
- 查询、合计和导出仍经统一薪资报表服务；上线后须分别核对明细与汇总，并确认总金额恒等。
