# 008 渼约旧服务历史读取

- 来源仅为旧渼约 `morestore:3306` 的 `eb_order_work`：状态 4（已完成）或 6（服务完成待评价），且有 `hx_time>0` 的工作单。来源只读，旧销售订单、未完成预约、聊天服务记录不单独生成服务。
- 目标仅为 `008.cc3798.com` 的 `mohe_008:3307`。沿用已验收的旧会员 UID → 008 UID 映射。用户决定：能查看该客户时，可查看其旧站全部门店的历史服务；新 V3 服务事实继续按商家账号的可见门店过滤。
- 旧站 2026-10-13 晚间仍在产生服务；只读预检由 49,635 变为 49,636 张，因此不把变动中的行数和摘要伪装成发布时固定数据。用户决定以发布时的一致性快照为截止点，此后新服务以 008 为准。`apply` 在一次来源只读一致性事务中冻结截止秒、行数与 SHA-256，并写入 008 独立批次；以后 `verify` 只核该冻结快照，不受旧站之后新记录影响。PoPo 旧 UID 421 的旧工作单 51080 必须在快照中。旧工作单用一行汇总其项目名称及已用次数；未存具体项目时明确显示“服务项目未记录”。
- SQL 只建立 `eb_mobile_customer_legacy_service_record` 只读展示快照及 `mig_morestore_20261013_service_history_batch` 批次表。不会写 V3 服务、核销、业绩、工资、卡项余次或客户最近到店统计。旧记录在手机商家端服务页按完成时间与 V3 记录合并分页，不加来源标签；数据库保留旧工作单 ID、旧会员 ID、旧门店、逐行来源摘要供追溯。
- 前提：产品经理对固定代码、来源筛选和发布时快照策略验收，并单独授权仅向 008 部署、增表和导入历史快照。发布时先执行 SQL、再执行 `php scripts/import/customer_008_morestore_service_history.php check`；确认预检范围和 PoPo 样本后设置已验收 commit 运行 `apply`，立即 `verify`，最后部署后端服务代码并用 PoPo 与跨门店权限实测。源码其他实例、旧站和 008 已有业务事实保持原状。
- 源工作单有 `do_time` 时以其开始时间加记录的服务分钟数作为完成时间；缺少开始时间时用核销时间。旧系统只提供工作单粒度，多个关联项目显示在同一条记录中；不虚构逐项目的单独完成时间或账务事实。
