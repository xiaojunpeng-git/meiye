# 008 商品排序归零

## 范围与来源

- 目标仅为 `008.cc3798.com` 的 `mohe_008.eb_store_product.sort`。页面“商品列表→排序”直接读取该列。
- 线上只读快照：商品 6,404 条，`sort <> 0` 的 2,483 条；其中未删除且上架 1,823 条、未删除且下架 660 条。19 条已删除商品排序原本均为 0。
- 将这 2,483 条排序值设为 0；其余商品本来就是 0，不写入。不改分类排序、门店副本排序、上下架、价格、库存、图片、会员资产或历史订单。
- 页面/商品查询常按 `sort DESC,id DESC` 排列；全部归零后相同条件下由后续排序字段决定顺序。
- `source-plan.json` 保存每条被改商品的 ID 与原排序值，既是固定执行守卫，也是定向恢复依据。用户要求不做全库备份；本批不做全库备份。

## 数据架构自检

- 权威源与粒度：商品主档 `eb_store_product`，每商品一条配置；不涉及业务交易事实或会员权益。
- 生效、历史与报表：排序只影响商品展示和后台列表顺序，不改变既有订单快照、经营事实、报表金额或统计时间。
- 事务、并发与幂等：执行前逐行比对固定快照并锁定当前商品行；一个 InnoDB 事务更新和登记升级记录。清单漂移、重复执行或部分状态均阻断。
- 权限与实例：只连 008 独立 MySQL 5.7:3307；仅清理 008 的商品缓存键；其他客户实例和共享进程不变。
- 恢复与对账：按 `source-plan.json` 的 ID/原排序值可定向恢复；执行后检查 6,404 条商品的排序均为 0、升级记录 1 条，刷新后台商品列表并核对样本。

## 执行门禁

1. 核对本地源码 HEAD、三文件 SHA-256、线上只读 `--action=check`、目标实例当前版本及商品表前态。
2. 产品经理对固定版本明确验收并授权仅 008 写入后，按准确文件清单本地提交；不推送。
3. 将固定执行脚本与清单临时传入 008，校验文件指纹后运行 `--action=apply --plan-sha=<清单SHA> --script-sha=<脚本SHA> --commit=<40位提交>`。
4. 运行 `--action=verify`，再做独立 SQL 和页面核对，记录执行结果并清理临时文件。
